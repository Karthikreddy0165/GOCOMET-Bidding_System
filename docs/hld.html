1. Purpose, scope and source alignment

An RFQ (Request for Quotation) lets a buyer request quotes from multiple suppliers. In this assignment, a British Auction is a reverse-bidding process: suppliers submit bids openly and can lower prices to compete. If qualifying bidding activity occurs close to the scheduled end, the auction may extend, but never beyond a configured forced-close time.

Design objective: deliver a simple, coherent application whose most important properties are correct bid processing, deterministic auction timing, visible progress and an auditable history. Start with a modular monolith; do not introduce microservices or Kafka without a demonstrated need.

In scope from the assignment

  • Create an RFQ with British Auction enabled, including reference/name, bid start, bid close, forced close and pickup/service date.
  • Capture supplier quote details including carrier, freight/origin/destination charges, transit time and quote validity.
  • Support configurable trigger window X, extension duration Y and the three stated extension trigger types.
  • Enforce forced close and validation rules.
  • Provide auction listing and details pages with lowest bid, closing times, status, supplier bids, rankings, quote details, configuration and activity log.

Explicitly out of scope for this submission

  • Payments, escrow, invoicing, shipment tracking and contract award workflows.
  • Microservices, Kubernetes, Kafka, Neo4j, multi-region deployment and complex analytics.
  • Automatic supplier invitation/matching unless added as a future product requirement.

Source alignment: these scope items follow the assignment brief, especially its sections on RFQ creation, British Auction configuration, validation, listing/details pages and deliverables. The brief does not prescribe a technology stack or numerical traffic target.

Capacity implications

  • Start with one FastAPI deployment, one PostgreSQL instance and one worker process for the assignment. Docker Compose is sufficient for local demonstration.
  • Keep the API stateless so additional instances can be added behind a load balancer if measured traffic requires it.
  • Use WebSocket room membership by auction_id. If multiple API instances are run, use Redis Pub/Sub (or another shared event bus) to distribute events between instances.
  • Do not claim a fixed server count from these assumptions. Benchmark the actual application; per-instance throughput depends on query cost, transaction duration, connection pool, CPU and memory.
  • Keep the critical bid transaction short. Ranking queries and indexes should be measured under concurrent bid tests.

6. Key data flows

6.1 Bid submission and live leaderboard update

  1. Client sends bid through REST with an idempotency key.
  2. Backend authenticates/authorizes supplier and begins a database transaction.
  3. Lock the auction row with SELECT ... FOR UPDATE. Check auction status and database time against effective close and forced close.
  4. Validate quote components and the supplier's previous accepted bid. Insert the bid and determine the updated ranking/L1.
  5. Evaluate extension rules against the current close time. If eligible, calculate min(current_close + Y, forced_close).
  6. Persist auction changes, extension record, activity record and outbox event in the same transaction; commit.
  7. Outbox publisher emits the event. WebSocket gateway broadcasts a role-appropriate payload to clients subscribed to that auction.

6.2 Auction extension logic

  • Trigger window is evaluated relative to the current effective close time, not the original scheduled close time.
  • Window condition: event time is at or after current_close - X minutes and before current close.
  • Evaluate only enabled trigger types: any accepted bid; any supplier rank change; or L1 supplier change.
  • Recommended assumption: at most one extension per accepted bid event, even if multiple enabled triggers match. Record all matching reasons.
  • New close time is MIN(current_close + Y, forced_close). If no time can be added, do not extend.

6.3 Auction closure

  • A periodic worker queries auctions where effective close time has passed and status is Active.
  • If forced-close time has passed, set status to Force Closed; otherwise set status to Closed.
  • Update and record closure in a transaction, then publish the status event.
  • Bid endpoint independently checks database time and rejects late bids. The worker is for state transition and notification, not the sole enforcement mechanism.

7. Database schema design

Use PostgreSQL. Store timestamps as TIMESTAMPTZ in UTC, monetary values as NUMERIC(14,2) (never floating point), and foreign keys for relational integrity. The schema below separates RFQ, auction configuration, supplier participation, submitted bids and audit history.

7.4 Important indexes and constraints

  • auctions(status, current_close_at) — find active/overdue auctions for the scheduler.
  • bids(auction_id, total_amount, submitted_at) — retrieve bids in price order.
  • bids(auction_id, supplier_id, submitted_at DESC) — find a supplier's latest accepted bid.
  • auction_activity(auction_id, created_at DESC) — load activity timeline.
  • outbox_events(published_at, created_at) — find unpublished events.
  • Check constraints: all charge components and total_amount are non-negative; X and Y are positive; forced_close_at > scheduled_close_at; current_close_at ≤ forced_close_at.
  • Use unique idempotency key per supplier/request scope. Add a unique constraint on RFQ reference and auction supplier membership.
Quote comparison assumption: ranking uses the sum of freight + origin + destination charges as total_amount. If the business compares only one charge or uses additional dimensions (tax, currency, accessorials), change the quote model and ranking rule before implementation. Currency should be explicit if multiple currencies are possible; this initial schema assumes one currency per RFQ.

8. Key design decisions, trade-offs and open questions

DecisionChoiceReason / trade-off
Application architectureModular monolithFast to build and deploy; clear module boundaries; avoids distributed-system overhead for assignment scale.
DatabasePostgreSQLStrong relational constraints, transactions, row locks, window functions and JSONB. MySQL/InnoDB could also meet the core requirements; PostgreSQL is a project choice, not a hard requirement.
Bid submissionRESTClear request/response validation, status codes and idempotency handling.
Live communicationWebSocketsPersistent bidirectional channel supports auction-room updates and future interactive events. REST + SSE would also work if only server push were required.
ConcurrencyPostgreSQL row-level lock on auction rowSerializes competing bid decisions for one auction while allowing different auctions to proceed concurrently. Keep transaction short to limit lock waits.
Background workCelery + RedisSuitable for periodic closure scans and retryable tasks. Do not rely on worker timing to enforce bid deadlines.
Cross-instance WebSocket fan-outRedis Pub/Sub when multiple API instances are usedSimple event fan-out. Pub/Sub is not durable; reconnecting clients must fetch a fresh snapshot. Outbox protects publication intent.
Event durabilityTransactional outboxPrevents a committed bid from losing its publication intent if the process crashes after database commit.
KafkaNot includedNo demonstrated high-volume replayable event-stream requirement in the assignment.
Neo4jNot includedNo graph-specific query or relationship requirement.

Open product questions to record (do not silently assume)

  1. Are competitor supplier identities and exact bid prices visible to suppliers, or are rankings anonymized?
  2. Is a supplier's next bid required to be strictly lower than its own previous accepted bid? Are equal bids rejected?
  3. How are equal total amounts ranked: earliest accepted bid first, shared rank, or another rule?
  4. Does one accepted bid cause at most one extension even if multiple trigger conditions match? Proposed rule: one extension per bid event, recording all matching reasons.
  5. Can buyer edit or cancel an auction after it becomes active?
  6. What currency, tax and additional charge components are supported?
  7. What is the required data retention and production availability target?

9. Delivery and validation checklist

  • ER schema migrated successfully with foreign keys, unique constraints and indexes.
  • Test two simultaneous bids against the same auction; verify serialized decisions and correct final L1.
  • Test two bids against different auctions; verify they do not block each other unnecessarily.
  • Test all three extension triggers, trigger-window boundaries and forced-close cap.
  • Test bid arriving exactly at or after current close and forced close.
  • Test duplicate idempotency key and transaction rollback.
  • Test WebSocket reconnect and snapshot resynchronization.
  • Test worker restart and recovery of overdue auctions and unpublished outbox events.
  • Run load test using the assumed peak profile; record p95 latency, error rate, lock waits and database CPU.
